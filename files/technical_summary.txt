TECHNICAL SUMMARY — Upwork API Support Bot
===========================================

ARCHITECTURE OVERVIEW
---------------------
A three-layer RAG pipeline:
  Ingestion  : PDF -> chunks -> ChromaDB
  Retrieval  : query -> top-3 chunks by cosine similarity
  Generation : chunks + system prompt -> Meta-Llama-3.1-8B via DeepInfra -> answer


DIFFICULTIES FACED
------------------

1. Chunking code snippets correctly.
   The Upwork API docs mix narrative prose with GraphQL query blocks. A naive
   fixed-size split often broke a code block mid-token (e.g., separating a curl
   flag from its value), giving the LLM incomplete context. Resolved by using
   RecursiveCharacterTextSplitter which respects paragraph/sentence boundaries
   before resorting to character splits, combined with the 50-character overlap
   so boundary-spanning snippets always appear in full in at least one chunk.

2. Preventing hallucination on out-of-scope questions.
   Without an explicit guard, the LLM would confidently answer questions whose
   answers are not in the documentation. Addressed via a two-part strategy:
   (1) the system prompt contains a hard-rule instruction: "base your answer
   ONLY on the context snippets provided", and (2) the user prompt explicitly
   labels the retrieved text as the exclusive knowledge source, making deviation
   syntactically inconsistent with the instruction.

3. LLM API latency.
   The DeepInfra endpoint round-trip for a 1k-token prompt can be 4-10 seconds
   depending on model load. The Streamlit spinner provides immediate user
   feedback; wall-clock latency is measured with time.time() and displayed as a
   st.metric so developers can see the true cost of each call.

4. Environment isolation for the embedding model.
   sentence-transformers downloads ~90 MB of model weights on first use. In a
   CI or cold-deploy scenario this adds significant setup time. The model is
   loaded once and cached with st.cache_resource, keeping subsequent query
   latency low.

5. Matching ingestion and query embeddings.
   ChromaDB stores raw vectors without metadata about how they were normalised.
   Using normalize_embeddings=True in both ingest.py and rag.py ensures query
   vectors and stored vectors live in the same unit-sphere space, making cosine
   similarity scores reliable.


HOW LLMs WERE USED IN DEVELOPMENT
-----------------------------------
- Claude (claude.ai) was used as a pair-programmer to draft the LangChain
  integration code, verify that ChatOpenAI's openai_api_base parameter correctly
  redirects requests to DeepInfra, and review the system prompt for ambiguous
  phrasing that could allow the model to bypass the hallucination guard.

- GPT-4 was consulted to cross-check the ChromaDB persistence API (specifically
  whether persist_directory in Chroma.from_documents is sufficient or whether an
  explicit .persist() call is still required in newer versions of
  langchain-community).

Every line of the final code was written, reviewed, and understood by me before
submission. LLM suggestions that I could not explain were discarded.
